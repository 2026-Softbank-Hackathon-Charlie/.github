# SoftBank Hackathon 2026 본선 제약사항 (Single Source of Truth)

이 파일은 본선 킥오프(2026-10-30) 내용을 에이전트가 따를 규칙으로 정리한 것이다.
모든 설계·구현·문서 결정은 아래 규칙을 우선한다. 규칙과 충돌하는 요청을 받으면 구현 전에 충돌을 사람에게 알린다.

## 0. 한 줄 요약

**가동 중인 프로덕션 앱을, 하나의 관리 체계로, 멈추지 않고 다른 환경(퍼블릭 A ↔ 퍼블릭 B ↔ 온프렘)으로 옮기고, 실패하면 되돌리며, AI 에이전트는 샌드박스에서 검증한 뒤에만 반영하는 "프로덕션 레벨 Multi-cloud Management Platform"을 만든다. Mock은 금지.**

## 1. 테마

- 공식 테마: **"Beyond Lock-in: Frictionless Cloud Management Across Platforms"**
- 예선 = 앱을 클라우드/온프렘에 *올리기*. 본선 = **프로덕션에서 가동 중인 시스템을 다른 환경으로 *이전하기***.
- "예선 배포 시스템을 토대로 프로덕션 레벨 멀티클라우드 관리 플랫폼을 만들어라." 운영 측도 난이도가 높다고 인정했다.
- 비즈니스 배경(발표에서 반드시 언급): 서비스마다 성능·보안 요구가 다르고, **반도체 메모리 가격 상승 → 서버 조달 비용 변화**, 클라우드 가격·정책도 계속 바뀐다. "클라우드를 여러 개 도입하는 것만으로는 해결되지 않는다." 목표는 온프렘/프라이빗/퍼블릭/AI 인프라를 특성에 맞게 쓰고 **필요에 따라 워크로드를 옮기는 것**.
- 보여줄 메시지: "멀티클라우드에 배포했다"(X) → **"하나의 관리 체계로 여러 환경을 다루고, 비용·정책이 바뀌면 옮길 수 있다"**(O).

### 전체 그림 (공식 다이어그램)

```
            Multi-cloud Management Platform (예선 배포 시스템 확장)
 ┌──────────────┬──────────────┬──────────────┬────────────────┬──────────────┐
 │ 무중단 이전  │ 보안·거버넌스 │ 온프렘 이전   │ AI 리소스/      │ 비용·횡단     │
 │ Zero-downtime│ Security &   │ (클라우드와   │ Data Residency │ 모니터링      │
 │ Migration    │ Governance   │ 동등 기능 재현)│                │              │
 └──────────────┴──────────────┴──────────────┴────────────────┴──────────────┘
   AI Agent: 샌드박스에서 점검·코드 변경·이전 계획을 자유롭게 시도 → 안전 확인 → 프로덕션 반영
        ↓                       ↓                        ↓
  Public Cloud A          Public Cloud B             On-prem
  (Google Cloud 등)       (AWS, NAVER Cloud 등)       (자신의 PC·VM)
        └──── 가동 중 이전 · 같은 기준으로 보호 ────┘
```

## 2. Hard Constraints (MUST, 위반 시 감점 또는 실격 수준)

1. **No Mock.** 어필하는 기능은 실제로 동작해야 한다. 데모 화면에 하드코딩 값, 가짜 진행 바, `setTimeout`으로 흉내 낸 결과, 고정 JSON 응답을 쓰지 않는다. 지표·로그·상태는 실제 소스(메트릭, 클라우드 API, 실제 요청)에서 온다. 개발 편의용 fake/stub은 테스트 코드에만 두고 데모 경로에서는 반드시 꺼진다.
2. **Live migration of a running app.** 이전 대상 앱은 이전 중에도 트래픽을 받고 있어야 한다. "멈추고 옮기기"는 예선 수준이다. 이전 중 에러율·지연·요청 성공률을 실시간으로 보여준다.
3. **Rollback(切り戻し) is first-class.** 데이터 동기화, DNS/트래픽 전환, **되돌리기 절차**를 모두 설계·구현한다. 실패 조건(예: SLO 위반, health check 실패)에서 자동 또는 1-click 롤백이 실제로 동작해야 한다.
4. **On-prem 포함.** 퍼블릭 클라우드 최소 1개 + 온프렘(자신의 PC 또는 그 위 VM) 환경을 관리 대상으로 넣는다. 클라우드 매니지드 서비스의 온프렘 대체를 설계한다 (예: S3 → MinIO, Secrets Manager → Vault/SOPS, CloudWatch → Prometheus/Grafana, CloudTrail → 감사 로그 수집, IAM → OIDC/RBAC, 백업).
5. **AI Agent = sandbox-then-apply.** 에이전트는 프로덕션에 바로 실행하지 않는다. 흐름은 반드시 `조사 → 샌드박스에서 시도(점검/코드 수정/이전 계획 리허설) → 검증 결과 확인 → 승인 → 프로덕션 반영`이다. 에이전트 권한은 최소 권한(least privilege)으로 제한하고, 모든 행동은 감사 로그에 남긴다.
6. **Tool-using agent.** 단순 LLM 호출(프롬프트 → 텍스트)이 아니라 도구를 쓰는 에이전트(Agents SDK / Agent SDK, tool calling, MCP 등)로 만든다.
7. **평가 대상은 플랫폼 품질.** 관리 대상 앱은 단순해도 되지만, **어디가 프로덕션 레벨인지 보이게** 한다 (상태를 가진 DB, 종속 서비스, health check, SLO, 로그/메트릭). 앱 개발에 시간을 쓰지 말고 플랫폼에 집중한다.
8. **Depth over breadth.** 모든 관점을 다 하지 않는다. 하나(또는 긴밀히 연결된 소수)를 골라 프로덕션 레벨까지 깊게 판다. 넓고 얕은 기능 추가 요청은 우선순위를 낮추자고 제안한다.
9. **데모 체크리스트 3종이 모두 화면에 나와야 한다.**
   - (a) 가동 중인 앱을 환경 간 이전하는 모습
   - (b) 여러 환경의 보안·거버넌스 상태 시각화 (GuardDuty, Security Command Center 등 벤더별 기능을 통일된 뷰로)
   - (c) AI 에이전트가 샌드박스에서 점검·수정하는 모습
10. **발표는 슬라이드가 아니라 설계 문서(Notion)로 한다.** 설계 문서 자체가 채점 자료다. 발표에서 말 못 한 고민 포인트(트레이드오프, 대안 비교, 장애 대응)는 문서에 구체적으로 적는다.
11. **예산.** 팀당 지원금 50만 원(네이버페이, 인프라+AI 비용). 초과분은 자비. 쓰지 않는 GPU·대형 인스턴스·NAT Gateway·Load Balancer는 즉시 내린다. 리소스는 IaC로 만들고 `destroy` 가능하게 유지한다.
12. **Secrets.** API 키·클라우드 자격증명은 코드·커밋·로그·설계 문서에 넣지 않는다. `.env`는 gitignore, 데모 화면에도 노출 금지.

## 4. 심사 기준 (100점)

| 항목 | 배점 | 무엇을 보는가 |
|---|---|---|
| 완성도·데모 | **30** | 관리 플랫폼이 실제로 동작해서 가동 중 앱의 환경 간 이전, 보안 상태 시각화 등을 **즉시** 시연할 수 있는가 |
| 클라우드 활용 수준 | **30** | 여러 환경을 묶는 관리 기능(포터빌리티, 보안, 거버넌스, 비용, AI 리소스)이 적절히 추상화·설계되었는가. 무중단 이전·롤백·권한 관리 등 프로덕션 운영을 상정했는가 |
| 팀 개발 | **20** | 팀워크로 성과를 극대화했는가. 설계 문서화가 잘 되어 있고, 대안 제시와 검토를 거쳐 현실적 범위로 전체 구조를 구성했는가 |
| 재미·독창성 | **10** | 독자적인 디테일·고민 포인트·아이디어 (확장성, UX 등 방향 자유) |
| AI 활용 | **10** | AI 에이전트 활용에 창의적 고민과 시도가 있는가 (샌드박스에서 점검·코드 변경 등) |

※ 최종발표뿐 아니라 **개발 중 모습과 중간보고**도 평가에 반영된다.

### 점수로 번역한 작업 원칙

- 60점(완성도 30 + 클라우드 30)은 "실제로 동작하는 데모 + 깊은 클라우드 추상화"에서 나온다. 기능 하나를 더 넣기보다 핵심 흐름이 끝까지 실제로 도는 것을 우선한다.
- "추상화"가 채점 문구다. 벤더별 구현을 공통 인터페이스(예: `Provider`/`Adapter`) 뒤에 두고, 새 환경 추가가 어댑터 하나 추가로 끝나게 설계한다.
- 팀 개발 20점: 작은 PR, 의미 있는 커밋 메시지, 이슈/PR에 설계 근거 링크, ADR(Architecture Decision Record) 형식으로 대안 비교를 남긴다. 에이전트가 만든 변경도 PR 설명에 "왜"를 적는다.

## 5. 프로덕션 레벨 체크리스트 (설계·구현 시 확인)

무중단 이전
- [ ] 데이터 동기화 전략 명시 (예: logical replication/CDC, dual-write 금지 또는 근거, 오브젝트 스토리지 sync)
- [ ] 트래픽 전환 방식 명시 (DNS TTL, weighted routing, LB/프록시 기반 canary·blue-green)
- [ ] 전환 게이트: health check + SLO(에러율, p95 지연) 기준
- [ ] 롤백 트리거와 절차, 롤백 후 데이터 정합성 처리
- [ ] 장애 주입(fault injection)으로 롤백을 실제로 시연 가능

보안·거버넌스
- [ ] 벤더별 보안 신호를 공통 스키마로 정규화해 한 화면에 표시
- [ ] 권한 관리(RBAC/least privilege), 승인 흐름, 감사 로그
- [ ] 온프렘에서 IAM·시크릿·감사 로그·모니터링·백업을 재현하고 가시화

AI 에이전트
- [ ] 샌드박스 격리(별도 네임스페이스/컨테이너/계정), 프로덕션 자격증명 접근 불가
- [ ] 계획(plan) → 리허설 결과 → diff/영향 범위 → 사람 승인 → 적용
- [ ] 에이전트의 tool 호출과 결과가 로그·UI에 실시간으로 보임

비용·데이터 레지던시 (선택한 경우)
- [ ] 비용 근거는 실제 가격 API 또는 출처가 명시된 단가표
- [ ] 데이터가 어느 리전/환경에 있는지 표시하고 정책 위반 시 이전 차단

## 6. 우선순위 / 피해야 할 것

DO
- 데모 시나리오(5분)에서 거꾸로 설계한다: 설명 1분 → 이전 데모 → 장애 주입·롤백 → 보안 뷰 → 에이전트 샌드박스.
- 실시간 지표·실제 로그를 화면에 띄워 "진짜"임을 증명한다.
- 데모가 실패할 때를 대비한 사전 녹화와 재시작 스크립트를 준비한다 (단, 라이브 시연이 기본).
- 비즈니스 이유(메모리 가격 → 온프렘 비용 변화 → 워크로드 재배치)를 플랫폼 기능과 연결한다.

DON'T
- Mock UI, 가짜 데이터, "여기서 실제로는 ~됩니다" 식 설명.
- 관리 대상 앱의 기능 개발에 시간 쓰기.
- 모든 관점을 얕게 다 넣기.
- 에이전트에게 프로덕션 직접 쓰기 권한 주기.
- 비용 큰 리소스를 켜 둔 채 방치하기.
- 슬라이드 제작 (설계 문서로 대체).

## 8. 에이전트 행동 규칙

- 새 기능을 제안·구현하기 전에 "어느 심사 항목 점수를 올리는가"와 "데모 체크리스트 (a)(b)(c) 중 무엇에 기여하는가"를 한 줄로 적는다.
- Mock/stub을 데모 경로에 넣어야 할 것 같으면 구현하지 말고 먼저 사람에게 묻는다.
- 클라우드 리소스를 만드는 코드는 비용 추정과 정리 방법(`destroy` 명령)을 함께 남긴다.
- 설계 결정은 `docs/adr/` (또는 Notion 설계 문서)에 대안·트레이드오프와 함께 기록한다.
- 출처 원문: 본선 킥오프(2026-10-30) 영상 요약 및 공식 심사 기준 안내.
